ASHENFALL — Registre des risques

Dernière mise à jour : 2026-10-22 (audit M4.4, documentation seulement).

#RisqueGravitéRéductionStatut
R1Personnages 3D modulaires : armures sur un squelette commun sans clipping ; gros travail Blender manuel. Les scripts ne produisent pas de modèles de qualité professionnelle.ÉlevéeSquelette unique figé tôt ; 2 à 3 pièces au départ ; preuve de concept en M3b ; placeholders jusqu'à M11 ; licences des assets tiers vérifiéesOuvert. Preuve de concept M3b validée (2026-10-21) : un squelette, deux armures de torse interchangeables, animations conservées ; reste le travail artistique réel
R2Sauvegarde : perte de données, changement de format, références cassées. Sur Web, stockage navigateur parfois purgé.ÉlevéeJSON versionné ; identifiants stables ; tests de chargement d'anciennes sauvegardes ; export/import de sauvegarde envisagé. M9.1 : format versionné avec migrations, copie de secours, contenu illisible conservé, version plus récente jamais écrasée (28 tests) ; reste l'export/import et la sauvegarde hors du navigateur (R52)Ouvert (atténué en M9.1)
R3Build Web : poids du build, mémoire limitée, compatibilité du navigateur mobile non garantie.ÉlevéeBuild Web dès M0 puis à chaque jalon ; budget de taille fixé tôt ; profil graphique Web strict. M11.1 : budget fixé (D296), trois profils graphiques dont Basse et Moyenne adaptés au Web, build de diffusion de 10,3 Mo téléchargés mesuré ; reste le mobile et les postes modestes (R54)Ouvert (atténué en M11.1)
R4Unity 6000.6.6f1 non-LTS : stabilité moindre, paquets tiers parfois en retard.MoyenneVersion figée ; migration vers une LTS seulement sur validation, tôt si besoinOuvert
R5Espace disque sur C: (environ 16 Go libres au 2026-10-20). Un seul disque visible.MoyenneLibérer de l'espace avant M0 étape 2 ; surveiller à chaque jalon ; LFS pour les gros binairesOuvert
R6Dérive de périmètre : brief riche (cosmétiques, builds, factions).MoyennePérimètre = vertical slice ; idées nouvelles au backlog (Docs) et validées avantOuvert
R7Animation de combat : style, qualité et intégration.MoyenneAnimations simples au départ ; retour visuel lisible avant la beautéOuvert
R8Outils MCP tiers : code externe pilotant l'éditeur ; licence, sécurité, compatibilité Unity 6.6 / Blender 5.2 non vérifiées.Faible à moyenneReportés ; évaluation après M0 ; aucune installation sans validationReporté
R10Clavier AZERTY / QWERTY : les touches sont liées par position physique, ce qui est censé donner ZQSD sur AZERTY. Dans le build Web, l'affichage du debug indique « W A S D » et une disposition vide : l'affichage des noms de touches ne reflète pas la disposition. Le fonctionnement réel sur AZERTY n'a pas pu être vérifié par moi.MoyenneTest par le porteur du projet sur son clavier (éditeur et navigateur) ; si besoin, schémas de contrôle séparésDéplacement validé dans Unity par le porteur du projet (2026-10-20) ; comportement dans le navigateur à confirmer
R11Sensation de jeu : valeurs de départ (vitesse 6, accélération 45, décélération 60) non éprouvées à la main.FaibleRéglage dans l'Inspecteur pendant les essaisClos (2026-10-20) : valeurs validées par le porteur du projet
R12Clic dans le navigateur : sur Web, l'état du pointeur est lu image par image ; un clic de 0 ms (envoyé par un outil automatique) ne se comporte pas comme un vrai clic. L'enregistrement du clic par événement corrige le cas des clics très brefs. Le clic droit ouvrira le menu du navigateur : à traiter avec les compétences.FaibleVérifié avec des clics de 120 à 150 ms ; prévoir un blocage du menu contextuel au jalon des compétencesOuvert
R13Détection de frappe : repose sur Collider.ClosestPoint (colliders convexes uniquement) et sur un point d'origine à hauteur de poitrine. Les gros ennemis ou les formes non convexes demanderont des ajustements.FaibleRéévaluer avec les vrais ennemis (M4/M5)Ouvert
R14Touche Espace dans le navigateur : Unity n'empêche pas le comportement par défaut du navigateur (défilement de la page). Dans le gabarit actuel la page ne défile pas (hauteur de page égale à la fenêtre), mais une fenêtre plus petite ou un autre gabarit pourrait la faire défiler.FaibleÀ surveiller ; bloquer preventDefault dans le gabarit Web si cela se produit. Vérifié sur les builds : l'esquive fonctionneOuvert
R15Équilibrage de l'esquive et des statistiques : distance, cooldown, endurance et formules de statistiques sont des valeurs provisoires, sans ennemis pour les éprouver.FaibleRéglage dans l'Inspecteur après les essais, puis avec les ennemis (M4/M5)Ouvert
R16Joueur sans ennemis : l'invulnérabilité n'était pas testable en situation réelle avant M4 ; testée par la commande de debug (T) et des tests automatiques.FaibleRetirer la commande de debug et le diagnostic d'esquive une fois l'invulnérabilité validée contre de vraies attaques ennemiesClos (2026-10-21) : validé contre les attaques ennemies de M4.2 ; touche T et diagnostic retirés (D96)
R17Esquive qui semble ne pas partir : la cause identifiée est corrigée (le joueur se blessait lui-même, voir D41) et la mémorisation allongée (D42). Autre cause matérielle possible, non reproductible par un test : certains claviers ne gèrent pas toutes les combinaisons de touches (ex. deux touches de déplacement en diagonale + Espace), l'appui n'arrive alors pas jusqu'à Unity.MoyenneDiagnostic : « Espace vu par Unity » compare ce que Unity voit à ce que reçoit l'action ; si des appuis manquent, proposer une seconde touche d'esquiveClos (2026-10-21) : validé par le porteur du projet après le test avec diagnostic (tous les appuis comptabilisés)
R18Appuis très précoces (pendant les ~0,25 premières secondes d'une esquive) refusés par conception : la zone morte est maintenant signalée (barre orange) mais pas supprimée.FaibleRéévaluer avec le ressenti ; ne pas réduire le cooldown sans accordOuvert
R19Qualité artistique du nain : le prototype généré par script reste un assemblage de formes simples (aspect « jouet » : crête plate, gantelets en blocs, barbe qui ne dépasse pas de la silhouette). Le pipeline est conçu pour que des modèles faits à la main ou sous licence se branchent sur le même squelette.MoyenneValidation visuelle de la silhouette avant tout détail ; décision du porteur du projet sur la méthode (script amélioré, modélisation manuelle, assets sous licence)Ouvert (checkpoint M3b.1)
R20Écart entre taille visuelle (1,51 m) et capsule (2 m) : à l'écran, le nain paraît plus petit que son collider ; les coups reçus des futurs ennemis toucheront la capsule, pas le visuel.FaibleMesurer à l'intégration (M3b.2) et avec les ennemis ; ne rien changer sans accordOuvert
R21Contraste du nain sombre sur sol sombre : en V2 le fer noirci domine ; à la taille réelle de jeu, sur le sol gris foncé de la Sandbox, la lisibilité baisse.MoyenneGarder des arêtes et accents plus clairs (acier usé, bronze), éclaircir ou nuancer le sol du jeu plus tard, juger dans la scène Unity (M3b.2) et pas seulement sur les rendusOuvert
R22NavMesh à l'exécution : génération synchrone au chargement (7 ms éditeur, 46 à 56 ms sur le Web pour le Sandbox) ; elle croîtra avec la taille des niveaux ; îlots navigables inatteignables dans les obstacles larges (inoffensifs) ; pas de mise à jour si le décor bouge.FaibleMesure à chaque jalon M4 et à M9 ; repli documenté : NavMesh précalculé et paquet AI Navigation (validation requise)Ouvert (M4.1)
R23Ennemis et performances Web : trajets, évitement entre agents, OnGUI des étiquettes de debug (coûteux sur Web et mobile), un personnage = 4 maillages skinnés.MoyenneTrajets espacés (0,2 s) et conditionnels ; étiquettes de debug désactivables ; mesurer à M4.4 (2 à 3 ennemis) ; registre d'ennemis sans recherche par image (audit M4.4)Ouvert (M4.1)
R24Valeurs d'attaque ennemie et lisibilité : 10 dégâts, anticipation 0,60 s, fenêtre d'esquive utile d'environ 0,2 s, garde de 0,35 s sont provisoires ; le joueur a 100 PV sans régénération, donc dix coups tuent ; indicateur et vignettage sont des retours provisoires (OnGUI) ; la sortie d'arc par la seule course est difficile (arc de 100° à 1,5 m), l'esquive la résout.Faible à moyenneRéglage dans EnemyBruteClub, EnemyDefinition et PlayerDamageFeedback après les essais manuels ; ne pas toucher aux valeurs du joueur ; régénération et soins : plus tardOuvert (M4.2)
R25Verrouillage permanent de l'ennemi par interruption : un joueur qui frappait sans arrêt empêchait toute attaque ennemie. Mesures historiques, scénario de 30 s à un coup toutes les 0,45 s. Avant correctif (éditeur) : 17 attaques lancées, 17 interrompues, 0 terminée, 0 coup reçu. Après correctif (WebGL réel) : 15 lancées, 8 interrompues, 7 protégées, 7 terminées, 7 coups reçus (éditeur : 16, 8, 8, 8, 7). Correctif : riposte protégée après une vraie interruption (D112 à D116). Les attaques protégées restent évitables (esquive, sortie de zone, mur, invulnérabilité) : le correctif n'introduit aucun coup garanti.FaibleRéglages possibles sans code si le ressenti change : protection temporelle et fenêtre d'interruption (EnemyDefinition)Corrigé et validé manuellement — clos (M4.3, 2026-10-21)
R26Recul près des obstacles : NavMeshAgent.Move et NavMesh.Raycast sont précis à environ 0,1 m (érosion du NavMesh, voxels) ; un obstacle sans collider ou un autre agent n'est pas pris en compte ; seul l'ennemi du Sandbox est testé.FaibleRevoir à M4.4 (plusieurs ennemis)Surveillé : le SphereCast du recul voit les colliders des autres ennemis (D147) ; aucun défaut constaté dans les tests à trois ennemis de M4.4.2 et M4.4.3 (interruption d'un ennemi entouré, évitement) (audit 2026-10-22) : avec plusieurs agents, le recul peut pousser un ennemi vers un autre ; tests de recul entre deux ennemis et contre un obstacle sans collider à ajouter ; surveiller tremblements et bouchons (CDC M4.4 §10, §12)
R27Cadavre et zone de réapparition : la réapparition ne vérifie que le joueur (pas d'autres ennemis ni d'objets) ; l'enfoncement de 0,6 m déplace le visuel seul sous un sol visible.FaibleÀ reprendre avec le butin et plusieurs ennemis (M4.4 et suivants)Corrigé et validé manuellement — clos (M4.4.3, 2026-10-23) : EnemyBrain.CanRespawn vérifie la permission de meute, le joueur à 2 m et l'emplacement occupé (borné à 10 s), délai écoulé conservé ; tests R01 à R07 (D152, D153)
R28Migration des commandes et des tests : le clic gauche d'attaque (maintenu, avec tampon de 0,15 s) est remplacé par la touche 1 ; environ 24 usages de leftButton dans les tests M2, M3, M3b.2 et M3b.3 sont à migrer sans perdre leurs garanties ; la liaison de la touche 1 est aujourd'hui prise par le debug d'équipement (D125).MoyenneMigration en M4.4.1 avec un test par étape ; garder le tampon de l'esquive ; ne rien supprimer d'autreClos (M4.4.1, 2026-10-22) : migration faite, 269 tests passent ; touche 1 libre (debug sur F1/F2) ; validé manuellement

D131 : en cas de conflit, ne pas changer les commandes sans le signaler au porteur du projetOuvert (audit M4.4)
R30Orientation contre la visée : PlayerAim réimpose le regard vers le curseur à chaque image ; une orientation vers la cible pendant l'attaque (D119, D123) doit avoir priorité sans casser les timings ni la restitution du contrôle.MoyennePriorité explicite côté moteur, tests C15 et C20Ouvert (audit M4.4)
R31Alerte de meute et réengagement : l'alerte ne doit ni réveiller un membre en retour protégé ou mort, ni créer un état de meute bloqué qui empêche toute réapparition (CDC §13).MoyenneAlerte limitée aux membres disponibles ; état de meute dérivé des membres, jamais stocké séparément ; tests A03, R02 à R04Ouvert (audit M4.4)
R32Létalité des groupes : trois ennemis attaquant à leur rythme font environ 17 dégâts par seconde (3 x 10 par 1,8 s) ; le joueur (100 PV, sans régénération) peut mourir en 6 s sans esquive. R33Ligne de vue et alliés : la ligne de vue de M4.3 est coupée par n'importe quel collider (dont un allié) : un ennemi masqué par un allié retarde son attaque ; l'évitement les fait se contourner (test à trois ennemis réussi).FaibleTesté en M4.4.3 : un ennemi aligné derrière un allié le contourne et attaque (D156) ; aucune modificationMesuré, faible (M4.4.3)

R35Chevauchement après 10 s d'occupation d'un point de réapparition (limite de conception conservée, D161) : si un autre être vivant non joueur (ennemi, mannequin) occupe encore le point de départ 10 s après le premier constat, l'ennemi réapparaît quand même en le chevauchant ; rien n'est déplacé de force, l'évitement du NavMesh écarte les agents. Valeurs de M1 et M3, validées à l'époque, jamais ajustées contre de vrais ennemis variés.MoyenneNe pas modifier avant M5.3 ; passe de réglage dédiée après M5.3 (distance, cooldown et coût d'endurance de l'esquive, vitesse) ; en attendant, les ennemis (dont l'élite M5.2) sont conçus en en tenant compte, sans compenser par des PV ou des dégâtsRésolu pour cette première itération (M5.4, validé le 2026-10-23) : réglage dans PlayerMobility.asset (D184, D185). R38Élite M5.2 : valeurs de départ non équilibrées, difficulté dépendante de la mobilité du joueur (R37), visuel et animations provisoires : à 6 m/s et avec l'esquive actuelle, la charge et le balayage sont faciles à éviter ; le résultat attendu (un combat « exigeant ») dépend du réglage de la mobilité prévu après M5.3. R40« En combat » peut durer tant qu'un ennemi vous poursuit (conséquence voulue de D176/D177) : un ennemi engagé à distance (tireur, ennemi qui contourne un obstacle) verrouille l'équipement tant qu'il est en Chase, Attack ou Stagger. Le joueur en sort toujours en tuant l'ennemi, en s'éloignant à plus de sa distance de perte de cible (14 m pour les ennemis ordinaires, 16 m pour l'élite) ou en le faisant dépasser sa laisse, puis en attendant son retour ; il n'y a pas d'issue « bouton » en pleine mêlée, par choix de gameplay. À surveiller si une rencontre future rend la sortie de combat trop pénible (ex. ennemis très rapides).FaibleTest dédié (le combat retombe à la mort, à l'abandon et au retour) ; ajuster les rayons d'abandon ou ajouter un état « hors de portée » si besoinOuvert (M5.3)
R41Compétences M6.1 : valeurs de départ non équilibrées, visuels et animation provisoires, effets limités : dégâts, coûts, cooldowns et durées n'ont été essayés que par tests et sur le Sandbox ; le « contrôle » de l'Onde de choc est un recul et un bref Stagger de coup normal ; la Frappe brise-garde peut interrompre l'élite après le verrouillage (risque que la Sentinelle devienne trop facile si le joueur chronomètre bien, borné par 8 s de cooldown, 25 d'endurance, la protection de 1,2 s et la riposte protégée) ; la Garde de fer (-50 % pendant 4 s tous les 14 s) peut trop affaiblir certains combats.MoyenneRégler après essai (cooldowns, coûts, valeurs, durée de la garde) ; ne rien compenser par des PV ou des dégâts d'ennemis sans accord ; vraies animations et effets avec les vrais assetsOuvert (M6.1) ; présentation affinée en M6.2 (visuels toujours procéduraux et provisoires, sans son)
R42Effets M6.3 : fondation sans contenu canonique, limites connues : les quatre effets sont des outils d'essai ; un malus de statistique ne peut viser que quelqu'un qui a des statistiques (les ennemis n'en ont pas) ; un poison sur un ennemi au repos ne le réveille pas (un tick n'est pas un coup) ; la puissance d'un effet ne dépend pas des statistiques de sa source ; pas de dissipation ni de résistance ; pas de sauvegarde ; temporisation sur Time.time (à rendre autoritaire côté serveur pour le multijoueur, l'architecture s'y prête : identifiant stable, source conservée, échéances explicites).FaibleCompétences de classe et statistiques d'ennemis dans un jalon ultérieur ; règle de réveil à définir si une compétence de dégâts sur la durée devient canoniqueOuvert (M6.3) ; mécaniques validées, suite = M6.4
